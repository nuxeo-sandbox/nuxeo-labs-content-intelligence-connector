# AGENTS.md

Nuxeo plugin connecting Nuxeo Platform (LTS 2025) to Hyland Content Intelligence Cloud APIs (Knowledge Enrichment, Data Curation, Knowledge Discovery, Agents, Ingest, Content Lake).

Apply the global Nuxeo plugin rules from `~/.config/opencode/AGENTS.md` (jakarta.*, Log4j2, JUnit 4 + `FeaturesRunner`, modern Java, 4-space indent, `Framework.getService()`, `NuxeoException` wrapping, `@since 2025.XX` on new public API, MANIFEST.MF formatting, etc.).

## Layout

Maven multi-module (parent `pom.xml`, Nuxeo parent `2025.18`, current version `2025.22.0-SNAPSHOT`; latest released `2025.21.0`):
- `nuxeo-labs-content-intelligence-connector-core/` — all Java code, contributions, tests, Web UI assets
- `nuxeo-labs-content-intelligence-connector-package/` — Nuxeo MarketPlace package assembly

Java root package: `org.nuxeo.labs.hyland.content.intelligence`. Six service families: `enrichment` (KE), `datacuration` (DC), `discovery` (KD), `agents`, `ingest`, `contentlake`. Mirroring is mostly — but not perfectly — consistent:
- `service/<family>/` and `OSGI-INF/service-<family>-contrib.xml` exist for ALL six families.
- `authentication/AuthenticationToken<Family>.java` exists for all families EXCEPT `datacuration` (DC reuses Enrichment auth — no `AuthenticationTokenDataCuration`).
- `automation/<family>/` exists for `enrichment`, `discovery`, `agents`, `ingest`, `contentlake`. **`datacuration` has NO `automation/datacuration/` subpackage** — its sole op (`HylandKECurateOp`) lives under `automation/enrichment/` for historical reasons. Plus an extra `automation/ui/` package (UI-only ops like `CICGetUIBundleConfigOp`) and a top-level `automation/HylandCIGetContributionNamesOp.java`.

Shared base: `service/AbstractCICServiceComponent.java`, `service/AbstractServiceDescriptor.java`, `service/CICServiceConstants.java`, `service/ServicesUtils.java`, `http/ServiceCall.java`, `http/ServiceCallResult.java`, top-level `ContentToProcess.java`.

UI / data model contribs (ported from the Studio project, see `Studio source` below):
- `OSGI-INF/cic-ui-schemas-contrib.xml` → schemas in `resources/schemas/cic_*.xsd`
- `OSGI-INF/cic-ui-doctypes-contrib.xml` → doctypes / facets (requires the schemas component)
- `OSGI-INF/cic-ui-directories-contrib.xml` → vocabularies in `resources/directories/cic-*.csv`
- `OSGI-INF/cic-ui-bundle-contrib.xml` → registers the Web UI bundle html and appends it to the `web-ui` Web Resources bundle
- `OSGI-INF/deployment-fragment.xml` → installs the `web/nuxeo.war/**` resources and appends `i18n/messages*.json` to the platform i18n files
- `OSGI-INF/cic-enrichment-helper-contrib.xml` → enrichment helper wiring
- `OSGI-INF/automation-contrib.xml` → registers all `CIC.*` / `Hyland*.*` automation operations (must stay listed in `MANIFEST.MF`)
- Web UI assets under `resources/web/nuxeo.war/ui/nuxeo-labs-content-intelligence-connector/`:
  - `nuxeo-labs-content-intelligence-connector-bundle.html` — bundle entry point with all `<nuxeo-slot-content>` contributions (slot-content names prefixed `cic-`)
  - `elements/` — Polymer elements ported from Studio. Renamed from `kd-*` to `cic-kd-*` in 2025.19 for namespace consistency. Slot-content names were ALREADY `cic-kd-*` before the rename; i18n keys `label.ui.cic.kd-*` were intentionally kept unchanged for back-compat with Studio overrides (do not "fix" them). KD ask-question elements: `cic-kd-ask-question.html`, `cic-kd-ask-question-shared.html`, `cic-kd-ask-question-with-selected.html`. KD conversation: `cic-kd-conversation.html` + `cic-kd-conversation-libs.js`, wired via slot-content `cic-kd-conversation` (`DOCUMENT_ACTIONS` order=-20, icon `icons:question-answer`); passes `configName` (from the selected `CICAgentAndConfig`) through to `HylandKnowledgeDiscovery.startConversation` / `continueConversation`.
  - **Shared agent picker `cic-agent-and-config-picker.html`** (since 2025.19) — `paper-dropdown-menu` populated by `HylandKD.AvailableAgents`; notifies `selectedAgentId`, `selectedConfigName`, `selectedTitle`, `selectedDocId`. Used by BOTH `cic-kd-conversation` and `cic-kd-ask-question-shared` — replaced the prior `<nuxeo-document-suggestion>` + `SelectCICAgentAndConfig` page provider in the latter, and the raw `<select>` + custom `_loadAgents` plumbing in the former. Calls the op once on `attached` (`autoLoad=true` by default); public `load()` refreshes, `reset()` clears selection. **Do NOT confuse with `cic-agent-selector.html`** (separate element, separate purpose — see below).
  - **`cic-agent-selector.html`** — dialog-based agent picker embedded inside the `cicagentandconfig` and `cicagenticagentandconfig` create + edit layouts. Calls `CIC.GetAllAgents` (NOT the Studio JS chain `javascript.CIC_GetAllAgents`) and fires a custom `agent-selected` event consumed by each layout's `_onAgentSelected` handler to populate `dc:title`, `dc:description`, and `cic{,agentic}agentandconfig:agentId`.
  - **`cic-ui-config-page.html`** — admin-only drawer page (slot-contents `cicUIConfigMenuItem` in `ADMINISTRATION_MENU` order=100 + `cicUIConfigPage` in `ADMINISTRATION_PAGES`, route `administration:cic-ui-config`) with two `paper-tabs`:
    1. **Buttons tab** — lists the plugin's CIC slot-contents and generates copy/paste Studio override snippets via `CIC.GetUIBundleConfig`. The `_minimalOutput` checkbox (default `true`) emits body-less `<nuxeo-slot-content name=... slot=... order=... [disabled]></nuxeo-slot-content>` tags relying on Web UI's same-`name` patch semantics. BUT `_serializeOne` always falls back to the full `templateBody` for rows whose current `order` differs from `defaultOrder` (reorder = unambiguous full body), regardless of the checkbox.
    2. **Form snippets tab** — hardcoded catalog of the 7 reusable `forms/cic-*.html` elements (mirrors README "Reusable form elements") with per-row checkbox + assembled preview + "all view" / "all edit" shortcuts. Generates `<link rel="import" href="../../nuxeo-labs-content-intelligence-connector/forms/...">` + element-usage blocks with a header comment reminding users to adapt the relative `../../` path. **The forms catalog (`_forms` property) is hardcoded in the page; when adding/removing a `forms/cic-*.html` file, also update that catalog.**
  - `forms/cic-*-{view,edit}.html` — reusable per-schema form snippets referenced by the per-doctype layouts and by Studio overrides.
- Per-doctype layouts live at `resources/web/nuxeo.war/ui/document/<doctype>/nuxeo-<doctype>-<mode>-layout.html` (modes: `view`, `edit`, `create`, `metadata`, `import`); ported doctypes: `cicagentandconfig`, `cicagenticagentandconfig`, `cicagentsandconfigs`, `cicagenticagentsandconfigs`. Critical: Nuxeo Web UI's per-doctype layout resolver expects this exact path (`nuxeo.war/ui/document/<doctype>/`); do NOT nest under the plugin's bundle folder.
- Web UI i18n under `resources/web/nuxeo.war/ui/i18n/messages.json`, `messages-fr.json`, `messages-fr-FR.json` — all keys namespaced under `label.ui.cic.*` (e.g. `label.ui.cic.ke.*`, `label.ui.cic.kd-ask.*`)

When adding a new service family / contrib, update **all** mirrored locations AND register the contrib XML in `core/src/main/resources/META-INF/MANIFEST.MF` under the single `Nuxeo-Component:` header (exception: `deployment-fragment.xml` is auto-detected and must NOT be listed there). Strict JAR manifest format: comma-separated entries, **single space** of indent on each continuation line (not 4 spaces), and the file MUST end with a blank line — without the trailing blank line the last entry is silently dropped at runtime.

## Build / Test

```bash
mvn clean install -DskipTests   # build without tests
mvn -pl nuxeo-labs-content-intelligence-connector-core test   # tests only
mvn -pl nuxeo-labs-content-intelligence-connector-core test -Dtest=TestHylandKEEnrichOp
```

**Always run the full reactor build (`mvn -DskipTests clean install` from the repo root) after ANY Java change** — never just `-pl nuxeo-labs-content-intelligence-connector-core`. The package module must be rebuilt so the marketplace zip contains the updated JAR; otherwise redeploying the package ships stale code.

Tests require live Hyland CIC credentials. Without env vars set, `ConfigCheckerFeature` silently skips the corresponding test groups (logs `Missing CIC ... => no tests of ...`). The feature reads env vars and copies them into Nuxeo system properties (e.g. `CIC_ENRICHMENT_CLIENT_ID` → `nuxeo.hyland.cic.enrichment.clientId`).

Required env var groups (any subset enables that family's tests):
- Auth (always required): `CIC_AUTH_BASE_URL`
- Enrichment: `CIC_ENRICHMENT_BASE_URL`, `CIC_ENRICHMENT_CLIENT_ID`, `CIC_ENRICHMENT_CLIENT_SECRET`
- Data Curation: `CIC_DATA_CURATION_BASE_URL`, `CIC_DATA_CURATION_CLIENT_ID`, `CIC_DATA_CURATION_CLIENT_SECRET`
- Discovery: `CIC_DISCOVERY_BASE_URL`, `CIC_DISCOVERY_CLIENT_ID`, `CIC_DISCOVERY_CLIENT_SECRET`, `CIC_DISCOVERY_ENVIRONMENT`
- Agents: `CIC_AGENTS_BASE_URL` + **`CIC_DISCOVERY_CLIENT_ID` / `CIC_DISCOVERY_CLIENT_SECRET`** — `ConfigCheckerFeature` really reads the *Discovery* env vars for the Agents client id/secret (l.260-263), so exporting `CIC_AGENTS_CLIENT_ID`/`_SECRET` alone leaves the Agents tests skipped. Deliberate or not, that is the current behavior; do not "fix" it without checking the CI-less release flow.
- Ingest: `CIC_INGEST_BASE_URL`, `CIC_INGEST_CLIENT_ID`, `CIC_INGEST_CLIENT_SECRET`, `CIC_INGEST_ENVIRONMENT`
- Content Lake: `CIC_CONTENTLAKE_BASE_URL`, `CIC_CONTENTLAKE_CLIENT_ID`, `CIC_CONTENTLAKE_CLIENT_SECRET`, `CIC_CONTENTLAKE_ENVIRONMENT`
- Test-only fixtures (not config params): `CIC_DISCOVERY_UNIT_TEST_AGENT_ID`, `CIC_DISCOVERY_UNIT_TEST_REPO_SOURCE`, `CIC_AGENT_FOR_UNIT_TEST`, `CIC_AGENT_KD_RAG_UNIT_TEST_AGENT_ID`, `CIC_INGEST_UNIT_TEST_REPO_SOURCE`, `CIC_CONTENTLAKE_UNIT_TEST_REPO_SOURCE`

Two more `ConfigCheckerFeature` traps when diagnosing "why are my tests skipped":
- the `*_BASE_URL` values are only **logged**, never ANDed into the `has*ClientInfo` gates (except via the shared `CIC_AUTH_BASE_URL`) — a missing base URL does not skip a group, it fails at call time.
- the Ingest branch logs `Missing CIC Content Lake Base URL => no Content Lake tests` (copy/paste in the message, not in the logic). Read the variable names, not the log text.

Full authoritative list and mapping: `nuxeo-labs-content-intelligence-connector-core/src/test/java/org/nuxeo/labs/hyland/content/intelligence/test/ConfigCheckerFeature.java`.

**There is no CI** — no `.github/workflows/`, nothing runs the build or tests automatically. The local root reactor build is the only gate.

**A green `mvn test` does NOT mean the CIC paths were exercised.** Only these tests actually run without any `CIC_*` env var:
- `TestCICEnrichmentEvent`, `TestCICEnrichmentEventIsolation` — `cicCallKEDone` event shape / rollback isolation
- `TestPartialConfigOverride` — same-name contribution merge + auth fail-fast
- `TestCICGetUIBundleConfigOp` — bundle HTML parsing
- `TestXMLContributions` — contrib registration
- `TestAutomationRegistration` — operation-ID uniqueness + every `@Operation` is registered (since 2025.22)
- `TestMiscAutomation` — `HylandContentIntelligence.GetContributionNames` + `HylandKnowledgeEnrichment.Configure`
- `TestCICEnrichmentWorkSession` — the async Work runs as the scheduling user, not as system (since 2025.22)
- `TestServicesUtils` — URL path/query encoding helpers + lenient boolean config parsing (since 2025.22)
- `TestServiceCallResult` — envelope building, round-trip, forceResponseAsJSONObject (since 2025.22)
- `TestCICEnrichmentHelper` — metadataJsonValueToString branches, boolean normalisation, ISO-date bullet (since 2025.22)

**The classification vocabularies extend `template-vocabulary` on `GenericDirectory`** (since 2025.22), not
`SQLDirectoryFactory` with a hardcoded `java:/nxsqldirectory`, so they follow whatever backend the server
template configures. Deliberately **no** `<require>org.nuxeo.ecm.directories</require>`: `DirectoryRegistry`
recomputes a directory when the template it extends is registered later, and the require would make the whole
component unresolvable wherever that component is absent — which is exactly what happens in this module's test
runtime. `TestXMLContributions.classificationVocabulariesShouldBeUsable` covers it and needs
`test-vocabulary-template-contrib.xml`, a test-only redeclaration of `template-vocabulary`, because
`nuxeo-platform-default-config` is not on the test classpath.

`TestXMLContributions.defaultKDContribLooksOK` used to assert `hasAllValues()` outright, so it **failed** (not
skipped) without the `CIC_DISCOVERY_*` env vars. Since 2025.22 it only asserts what the XML guarantees offline
(non-blank `tokenGrantType` / `tokenScope`) and gates the full check on `ConfigCheckerFeature.hasDiscoveryClientInfo()`.
The whole suite now really is green with no `CIC_*` variable set — verify with
`env $(env | grep ^CIC_ | cut -d= -f1 | sed 's/^/-u /') mvn -pl ...-core test` before claiming otherwise.

**`TestAutomationRegistration` scans the compiled `automation` package** for `@Operation` classes and asserts (a) no
two of them share an ID, (b) each one resolves through `AutomationService` to itself. It exists because
`ContentLakeGetDocumentOp` shipped with a copy/paste of `IngestCheckDigestOp`'s ID *and* was never registered — so
the Content Lake family had no automation surface at all, and naively adding the missing `<operation>` line would
have made the server fail to start on the duplicate ID. Do not replace the classpath scan with a hardcoded list:
the point is that a newly added operation is picked up automatically.

`RollbackThrowingKEDoneListener.java` (in the test package) is a **test-only fixture** used by `TestCICEnrichmentEventIsolation`, not production code.

## Code style (no tooling enforces it)

There is **no formatter config, no `.editorconfig`, no checkstyle/spotless** in the repo — the Nuxeo Java style is applied by hand (see the `Apply Nuxeo Java code style to the whole codebase` commit). What that pass actually normalized, and what a new contribution is expected to respect:
- hard wrap at 120 columns, no trailing whitespace, final newline on every file;
- no empty `@param` / `@return` / `@throws` Javadoc tags (~140 were removed) — write a description or drop the tag.
- **`@Operation` `description` string literals are user-visible in Studio.** The style commit was validated by extracting every string literal per file and diffing them byte-for-byte against the previous commit. Treat any reformatting that touches a string literal as a functional change and re-check it the same way.

## Conventions specific to this repo

- All operations return a JSON `Blob` with the canonical envelope `{ responseCode, responseMessage, response, objectKeysMapping? }`. Preserve this shape; never alter the upstream `response` payload.
- Each extension point supports multiple named contributions selected via the operation parameter `configName` (default `"default"`). New contributions are configured purely via XML + Nuxeo config params (`${nuxeo.hyland.cic.<family>.*}`) — see `OSGI-INF/service-<family>-contrib.xml` for the exact param names.
- **Never guess a `nuxeo.hyland.cic.*` param name from the family name — the naming is inconsistent, always copy it from the contrib XML.** Real cases: Enrichment mixes `nuxeo.hyland.cic.contextEnrichment.baseUrl` with `nuxeo.hyland.cic.enrichment.clientId` / `.clientSecret` / `.auth.grantType`; Data Curation mixes `nuxeo.hyland.cic.dataCuration.baseUrl` + `.auth.*` (camelCase) with `nuxeo.hyland.cic.datacuration.clientId` / `.clientSecret` (lowercase). Renaming them would break every existing `nuxeo.conf` — leave them alone.
- **Same-name contributions MERGE, they do not replace** (since 2025.20): `AbstractCICServiceComponent.registerDescriptorExtension` calls `existing.merge(descriptor)` when the name is already registered.
  - `AbstractServiceDescriptor.merge(other)` copies a field only when `StringUtils.isNotBlank(other.field)` — so neither an absent element (`null`) nor an empty one (`""`, the `${undefined.param:=}` case) can wipe a configured value. Side effect: a partial override cannot deliberately clear a field.
  - `merge()` resets the lazily built `authTokenParams` cache; forgetting that would keep pre-merge credentials.
  - **Any subclass declaring its own `@XNode` fields MUST override `merge()` and chain to `super`** — otherwise those fields are silently lost on override. Current overrides: `KEDescriptor` (`embeddingsFacet`, `embeddingsImageXpath`, `embeddingsTextXpath`, `pictureRenditionName`), `KDDescriptor` / `IngestDescriptor` / `ContentLakeDescriptor` (`environment`). `AgentDescriptor` and `DCDescriptor` have no own field.
  - **Checklist when adding a new `@XNode` field to a descriptor**: (1) getter, (2) `merge()` override in the subclass chaining to `super`, (3) declare it in `OSGI-INF/service-<family>-contrib.xml`, with a `${nuxeo.hyland.cic.*}` param when it is deployment-specific, (4) **update `README.md`** — the "About Hot Reload" chapter tells users to keep a FULL copy of the `default` contribution, so a new field must appear in that example, otherwise every existing copy silently goes stale, (5) `@since`.
  - Regression context: a Studio project contributed `<name>default</name>` with only the three `embeddings*` fields; the previous raw `contribs.put(...)` nulled `clientId`/`clientSecret`/`tokenGrantType`/`tokenScope` and enrichment died on a bare NPE in `URLEncoder.encode`, inside an async Work. Covered by `TestPartialConfigOverride` + `partial-override-configs.xml` (offline).
  - Diagnostic tell for this class of bug: `tokenGrantType` or `tokenScope` reported blank is **impossible** from the plugin's own XML (their `${...:=}` defaults are non-empty), so it always means another contribution replaced the descriptor.
- **Auth fail-fast** (since 2025.20): `AuthenticationToken.getToken()` calls `checkConfigOrThrow()` and raises a `NuxeoException` naming service + `configName` + missing fields. `AuthenticationToken` carries a `configName` (4-arg constructor; the 3-arg one is kept and passes `null`), propagated by all six `initAuthTokens(...)` call sites via `desc.getName()`. `initAuthTokens` also emits one single ERROR per incomplete config using `getMissingValuesAsString()`; `AbstractServiceDescriptor.checkConfigAndLogErrors()` is now `@Deprecated` and unused. `grant_type` is now URL-encoded like the other params (it was concatenated raw, so a null would have been sent as the literal `"null"`).
- Operation IDs are kept stable across the historical `nuxeo-labs-knowledge-enrichment-connector` plugin and this one — do **not** rename existing operation IDs. Lone exception, done in 2025.22: `ContentLakeGetDocumentOp` was renamed from `HylandIngest.CheckDigest` (a copy/paste of `IngestCheckDigestOp`) to `HylandContentLake.GetDocument`. That ID had never been registered in `automation-contrib.xml`, so it was never exposed and nothing could depend on it. Guarded by `TestAutomationRegistration`.
- **Global call tracing `nuxeo.hyland.cic.moreLogs`** (boolean, default `false`, since 2025.20): the ONLY plugin-wide config param — not per-family, not per-`configName`. Constants `MORE_LOGS_PARAM` / `MORE_LOGS_DEFAULT` + six `SERVICE_CODE_*` (`KE`, `DC`, `KD`, `Agents`, `Ingest`, `ContentLake`) live in `CICServiceConstants`. The `SERVICE_CODE_*` are deliberately distinct from the per-service `SERVICE_LABEL` constants (those are the long labels used in `CICError` messages).
  - Single entry point: `ServicesUtils.logCICCall(clazz, service, action[, target])` — it tests `isMoreLogs()` itself, so callers never guard it; target strings are built with `ServicesUtils.targetDocument/targetDocuments/targetBlobs`. Output: `Calling CIC KE/imageDescription for document <uid>`. `action=null` omits the `/action` part (used by `HylandKEInvokeOp`).
  - `isMoreLogs()` reads `Framework.getProperty` on **every** call — intentionally NOT cached in a static: the cost is nil next to the HTTP call, and a static would make both values untestable in the shared test JVM.
  - Wired today in KE only (+ `HylandKECurateOp`, which logs `DC/curate` since it actually calls Data Curation despite living in `automation/enrichment/`). KD / Agents / Ingest / Content Lake are intentionally NOT wired yet — the API and all six codes are ready so adding one is a one-liner.
  - **Since 2025.22 it also gates the two verbose payload dumps** in `HylandKDServiceImpl#invokeDiscovery` and `HylandKEServiceImpl#enrich`. They used to be `if (log.isInfoEnabled())`, i.e. emitted on every call in production since Nuxeo's root level is INFO — and the Discovery one dumps the questions typed by end users.
  - `configParamToBoolean` accepts `true`/`yes`/`on`/`1` and `false`/`no`/`off`/`0`, case-insensitively, and logs an error on anything else. It used to delegate to `Boolean.parseBoolean`, so `moreLogs=yes` silently disabled the traces, and its `catch (NumberFormatException)` was dead code.
  - In `AbstractCICEnrichmentOp` the two call sites sit immediately before `ke.enrich(...)` (single-doc and per-batch). The batch one is placed AFTER the `contentObjects.isEmpty()` guard so nothing is logged when no CIC call happens (consistent with the `NO_CALL` event status), and it reports `contentObjects.size()`, not `batch.size()`.
  - `HylandKEEnrichSeveralOp.run(DocumentModelList)` delegates to `run(BlobList)`; a `logTarget` field carries `"n documents"` so the single log emitted at the real call site doesn't degrade to `"n blobs"`. Keep that pattern if you add similar delegating overloads.
- **`metadataJsonValueToString` value rules** (`CICEnrichmentHelperImpl`): inside an array of objects, only `null` and the empty string are omitted. `0` and `false` used to be dropped by the JS falsy rule inherited from the Studio port — that was data loss and was fixed in 2025.22. Booleans, and the strings `true`/`yes`/`false`/`no` (case-insensitive), are normalised to `"true"`/`"false"`; **numbers are deliberately NOT coerced**, since turning `1` into `"true"` would corrupt an ordinary count such as `{"pageCount": 1}`.
- **The ISO-date bullet substitution is DELIBERATE.** A value matching `^\d{4}-\d{2}-\d{2}$` has its hyphens replaced with `\u2022`. Inherited from the Studio JS port, kept on purpose, and pinned by `TestCICEnrichmentHelper.shouldReplaceHyphensOfIsoDatesWithBullets`. Do not "fix" it.
- **`processBatch` must report FAILURE on an unexpected exception** (since 2025.22): its outcome accumulators are initialised to `SUCCESS`/`200`, so a `RuntimeException` escaping the `try` used to make the `finally` fire a `cicCallKEDone` event claiming success for a batch that was never sent. The usual trigger was `getBlob` raising `PropertyNotFoundException` on a heterogeneous selection; the text ops now check `hasSchema` first and return `null`, routing the document through the existing "No blob" path.
- **Unknown `configName` fails fast** (since 2025.22): `AbstractCICServiceComponent.getDescriptorOrThrow(configName)` throws a `NuxeoException` naming the service and listing the available configuration names. Every call path that builds a service URL uses it. The four `HylandKEServiceImpl` accessors `getEmbeddings*` / `getPictureRenditionName` keep using the nullable `getDescriptor(...)` on purpose: their contract is to return `null` or a default.
- **Auth token caching is synchronized** (since 2025.22): `AuthenticationToken.getToken()` is `synchronized`, and `token` / `tokenExpiration` are always set and cleared together via `invalidate()`. One instance is shared by every thread through the static per-service token maps, and the two fields were neither volatile nor guarded, so a reader could see a non-null token with a null expiration and NPE on `Instant.isAfter(null)`. An authentication error now clears the cached token instead of returning the stale, expired one.
- **HTTP error bodies are read** (since 2025.22): `ServiceCall.readErrorBody(...)` consumes `getErrorStream()` on any non-2xx, so the upstream diagnostic reaches `cic_error:fullResponseJson` instead of a bare `{}`. Consequence: `ServiceCallResult.toJsonObject()` must tolerate a non-JSON body (a gateway HTML error page), which `parseResponseOrRaw(...)` does by falling back to the raw string.
- **Global HTTP timeouts** `nuxeo.hyland.cic.http.connectTimeout` (30 s) and `.readTimeout` (120 s), since 2025.22, applied centrally in `ServiceCall.openConnection(...)`. `0` restores the previous "wait forever" behaviour. These are the second and third plugin-wide parameters, alongside `moreLogs`.
- **`requiresEnvironment()` must agree between the descriptor and the token.** `KDDescriptor` returned `false` while `AuthenticationToken.checkConfigOrThrow` required it for DISCOVERY, so an incomplete KD config raised no startup error and only failed at call time. Both sides now cover DISCOVERY, INGEST and CONTENTLAKE. `AuthenticationToken.requiresEnvironmentHeader()` stays narrower (DISCOVERY + INGEST only): Content Lake needs an environment to build its host name but has never been sent the `hxp-environment` auth header.
- **`MANIFEST.MF` oddities that are NOT defects**: `Bundle-Version: 1.0.0` is hardcoded and never tracks the Maven version — Nuxeo's own bundles do the same (`0.0.0.SNAPSHOT`, `1.0.0`, `5.4.2.qualifier`), and `2025.22.0-SNAPSHOT` is not even a valid OSGi version (a hyphen is not a qualifier separator). `Bundle-SymbolicName` is still `nuxeo-hyland-content-intelligence-connector-core` while the artifactId is `nuxeo-labs-...`: **do not rename it**, every `@Deploy(...)` in the tests and any third-party `Nuxeo-Require` uses the old name.
- **Never concatenate a caller-supplied value into a service URL raw** (since 2025.22). Use `ServicesUtils.encodePathSegment(...)` for path segments (agent / conversation / message / source / document ids) and `ServicesUtils.encodeQueryParam(...)` for query values (digest, contentType). `encodePathSegment` post-processes `URLEncoder` output to turn `+` back into `%20`, which is what a path segment requires; `_` is unreserved so the Content Lake `__` separator survives untouched. Covered offline by `TestServicesUtils`. The KE presigned-URL call used to encode the mime type by hand with `replace("/", "%2F")`, which silently turned `image/svg+xml` into `image/svg xml`.
- **Knowledge Enrichment is v2-only since plugin 2025.16** (v1 is deprecated and will be removed by Hyland). The `useKEV2` parameter on `HylandKnowledgeEnrichment.Configure` is ignored — passing `useKEV2=false` logs a WARN. The `nuxeo.hyland.cic.enrichment.v2` config param should not be set. Do **not** reintroduce v1 code paths.
- **KD polling sleep**: `HylandKDServiceImpl` polling loops (`getAnswer`, `askQuestionAndGetAnswer`) wrap `Thread.sleep` in a helper that restores the interrupt flag and re-throws as `NuxeoException` (matching the KE/DC pattern). The public KD service methods and the related automation ops (`HylandKDAskQuestionAndGetAnswerOp`, `CICKDAskQuestionForUIOp`) do **not** declare `throws InterruptedException`. When adding new long-polling code, use the same `sleepBetweenPullAttempts()`-style helper.

## Hot reload

- **A partial override of an existing config name does NOT survive a hot reload** (still true after the 2025.20 merge fix). `unregisterDescriptorExtension` does `contribs.remove(name)`, dropping the whole entry — including the plugin's own contribution, which is NOT re-registered: `applyStashWhenRunning` only deactivates/reactivates the components in `toRemove`/`toAdd`, i.e. the reloaded bundle. The config is then rebuilt from the Studio contribution alone.
- **A FULL copy does survive**: after the removal, re-registering hits the `existing == null` branch and `put()`s the complete Studio descriptor. This is why `README.md` "About Hot Reload" tells users to redeclare every field.
  - Residual trap: for fields the copy omits, cold start applies the plugin's defaults (via `merge`) but hot reload does not — behaviour can differ between a restart and a hot reload once the plugin adds a new field.
- Default strategy is `standby` (`ReloadComponent.RELOAD_STRATEGY_VALUE_DEFAULT`). `standby()` calls `stopComponents(true)` WITHOUT `deactivateComponents`, so component instances and their `contribs` field survive — which is exactly why the stale state persists.
- **`org.nuxeo.runtime.reload_strategy=restart` is NOT a workaround: the strategy is broken in Nuxeo.** `ReloadComponent.deactivate()` (l.118) nulls its own `protected static Bundle bundle`; the `restart` branch calls `componentManager.stop()` (l.209), which deactivates every component including `ReloadComponent` itself, then `undeployBundles()` (l.223) → `getBundleContext()` (l.102) → NPE. Verified in the deployed bytecode of 2025.24.15 and in the 2025.25-SNAPSHOT sources (file unchanged since 2023-01-24). Ticket filed with Nuxeo. Deliberately NOT mentioned in `README.md` — it is a dead end.
- **Planned fix (backlog, not implemented)**: keep the raw contributions per name (`Map<String, List<D>> rawContribs`) and recompute the effective descriptor into a FRESH instance on every register/unregister, mirroring Nuxeo's own `DescriptorRegistry`. Do NOT migrate to `DescriptorRegistry` itself: it is a single runtime-wide instance and `DefaultComponent.deactivate()` calls `clear()` on it, which wipes every component's descriptors.
  - Reproducible offline with `mgr.unregister(new ComponentName("org.nuxeo.labs.hyland.content.intelligence.test.partialoverride")) + mgr.unstash()` — the real `standby` unregister path. `HotDeployer.deploy/undeploy` goes through `refresh()` (restart semantics) and does **not** reproduce it.

## Polymer element conventions (lessons learned)

- **i18n property pattern (canonical)**: when a Polymer element exposes a `label`-like i18n property, the **correct** pattern is:
  - Property default: a plain-string i18n KEY (e.g. `value: 'label.ui.cic.kd-conversation'`), NOT a pre-translated string.
  - Template: resolve via `[[i18n(label)]]`, NOT `[[label]]` directly.
  - Canonical example in the platform: `nuxeo-operation-button` → `<span class="label">[[i18n(label)]]</span>`.
  This pattern lets any consumer (bundle, layout, Studio override) pass either an i18n key OR a pre-translated string — both work because `i18n('Already translated')` returns the input unchanged when no key match. It also fixes locale-freeze and makes the bundle author's mental model consistent (the `label="..."` attribute is always a key).
- **Antipattern — pre-translating in the property default**: `value: function() { return this.i18n('label.key'); }` was an earlier workaround but is itself flawed because (a) it stores a translated string in the property, so any consumer passing `label="some.key"` would have its key rendered raw if the template uses `[[label]]`, and (b) the translation is captured at first-render time, freezing the locale. Always prefer plain-key default + `[[i18n(prop)]]` template resolution.
- **NEVER call `window.nuxeo.I18n.translate(...)` at element-definition time** (i.e. as the literal `value:` of a `properties:` entry). It is evaluated once when `Polymer({...})` is parsed, BEFORE the user's locale is resolved AND potentially before `window.nuxeo.I18n` exists. Symptoms range from labels frozen in the wrong language to silent property-block invalidation (all properties lost → bound attributes ignored → e.g. `<paper-icon-button icon="[[icon]]">` renders with no glyph). The fix is the canonical pattern above (plain-key default + `[[i18n(prop)]]` in template), NOT a deferred `value: function()` that calls `this.i18n(...)`.
- **`this.i18n(...)` / `[[i18n(...)]]` requires a Nuxeo behavior** — the helper is NOT a Polymer built-in. Any element that uses `i18n(...)` (either in template bindings or in JS as `this.i18n('key')`) MUST declare `behaviors: [Nuxeo.LayoutBehavior]` (recommended — pulls `Nuxeo.I18nBehavior` transitively, plus filter helpers used elsewhere in the plugin) or at minimum `behaviors: [Nuxeo.I18nBehavior]`. Symptom of forgetting it: `this.i18n is not a function` in the console and every `[[i18n(...)]]` binding renders empty — the element silently appears broken. All Polymer elements in this plugin use `behaviors: [Nuxeo.LayoutBehavior]` — keep that as the default for any new element that does i18n.
- For `icon` properties on Polymer elements that wrap `<paper-icon-button>`, declare `reflectToAttribute: true` so the attribute reliably appears on the host (helps debugging via DevTools and ensures slot-content-passed values propagate cleanly).
- **Iconset prefix discipline**: the prefix BEFORE the colon in an icon id (e.g. `icons:foo`, `communication:bar`) is the iconset NAME, not a generic namespace. Each `@polymer/iron-icons/*-icons.js` file registers its own iconset:
  - `iron-icons.js` → iconset `icons` (general UI: `question-answer`, `arrow-back`, `more-vert`, `delete`, `settings`, `info`, `done`, `close`, etc.)
  - `communication-icons.js` → iconset `communication` (`forum`, `chat`, `chat-bubble`, `email`, `message`, `phone`, `contacts`, `vpn-key`, etc.)
  - `editor-icons.js` → iconset `editor`
  - `hardware-icons.js` → iconset `hardware`
  - `image-icons.js` → iconset `image`
  - `notification-icons.js` → iconset `notification`
  - `social-icons.js` → iconset `social`
  - `@nuxeo/nuxeo-ui-elements/nuxeo-icons.js` → iconset `nuxeo`
  Symptom of a wrong prefix: `<paper-icon-button>` renders the ripple/outline but no glyph; in DevTools the inner `<iron-icon>` element is empty (no `<g>` SVG child). Real-world example from this plugin: `icons:forum` was used but `forum` lives in iconset `communication` → had to be `communication:forum`. Cross-check with `elements/nuxeo-app.js` in the Nuxeo Web UI sources for the exact list of icon subsets it loads (see "Studio source" below for how to get those sources).
